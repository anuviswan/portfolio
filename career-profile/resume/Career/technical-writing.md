# Overview

I view technical writing as an engineering activity rather than an administrative task. Well-structured documentation improves collaboration, preserves knowledge and enables teams to make better technical decisions.

Throughout my career I have invested in documenting architecture, requirements, engineering practices and technical decisions to create maintainable knowledge rather than isolated documents.

---

# Documentation Philosophy

My documentation should:

- Be concise and easy to navigate.
- Explain *why*, not just *what*.
- Evolve alongside the software.
- Be useful to both humans and AI assistants.
- Remain version-controlled with the codebase whenever practical.

---

# Documentation Types

## Requirements

I prefer structured, traceable requirements with clear business outcomes, assumptions and acceptance criteria.

## Architecture

Architecture documentation should capture:

- Context
- Constraints
- Decisions
- Alternatives considered
- Trade-offs
- Long-term implications

## ADRs

I use Architecture Decision Records (ADRs) to document significant technical decisions so future engineers understand the reasoning behind them.

## Knowledge Base

I prefer maintaining an engineering wiki or knowledge base containing:

- Design notes
- Engineering standards
- Development workflows
- Lessons learned
- AI context

# API Documentation

API documentation should be:

- Accurate
- Example-driven
- Versioned
- Easy to discover
- Maintained alongside implementation

# Technical Writing Principles

- Write for the next engineer.
- Prefer clarity over verbosity.
- Document decisions, not just implementations.
- Keep documentation close to the source.
- Continuously refine documentation.
